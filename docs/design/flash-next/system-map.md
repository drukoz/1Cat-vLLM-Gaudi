## Assumptions

1. The base of all work is this fork (`drukoz/1Cat-vLLM-Gaudi`, identical to `1CatAI/1Cat-vLLM-Gaudi` `main` at `e2266e0`), not upstream `vllm-project/vllm-gaudi`. The request asks to audit 1Cat's kernels and reuse its DFlash2 work; upstream fixes are cherry-picked, not rebased onto.
2. The model is **Qwen3.8-Flash-Next** (`Qwen/Qwen3.8-Flash-Next`, architecture `Qwen4ExpForConditionalGeneration`); "Swift-1.5 Flash-Next" is the company's name for it. **No Flash-Next run exists yet on the Gaudi box.** Every measurement so far (section 11) used the dense Qwen3.8-27B (`Qwen3_5ForConditionalGeneration`), in BF16 or FP8, on the stock vllm-gaudi image or on this fork. The user has not quantized Flash-Next. The first Flash-Next bring-up is therefore **BF16 at TP8 on one server**, the only layout in which the 335 GiB checkpoint fits without host offload (section 2a); the production layout of two TP4 servers needs the published FP8 checkpoint or PLE host offload and comes later (M4).

4. The repository has no Dev branch; `main` is the base branch and the program's pull request targets it as a draft until the program is done.
5. Existing routes (Qwen3.5 / Qwen3.8-27B GDN, DeepSeek V4 / V4.1, MiniMax M3 / H3) must not regress, but get no new work.
6. **Engine pin.** The program builds against vLLM commit `8f816a3f665489d7f0d222115d4f72ebab01076b` (2026-09-04), the commit the user runs this fork against on the box. It already contains Flash-Next (260 commits after the 2026-08-31 merge). Later upstream Flash-Next fixes are backported into the plugin's own copy of the model (R4b lists them). Moving the fork to a newer vLLM (0.30.0 or later, where `_Fp8OnlineLinearBase` is gone and the V1 model runner was removed upstream) is a separate program, not this one.

## 1. Purpose and users

The repository is the Intel Gaudi hardware plugin for vLLM (`vllm_gaudi`, Apache-2.0), in 1CatAI's Gaudi2-focused fork, which adds Qwen GDN / DFlash2 paths, DeepSeek V4 / V4.1 native execution, FlashInfer-Gaudi operators and MiniMax support on top of upstream `vllm-project/vllm-gaudi` (`AGENTS.md`, `README.md`, `docs/1cat_gaudi_guide.md`).

For Rukoz Ent it serves one thing: the company's agent fleet. Paperclip's engineers, tech leads and reviewers call an OpenAI-compatible endpoint with long agentic contexts (about 128K tokens each), many concurrent sequences, long shared prefixes (system prompts, repository guides) and tool calls. Today the fleet is served from other machines; the Gaudi node is the target. The reference measurements in section 11 are that workload on the 27B model.

## 2. The model: Qwen3.8-Flash-Next

### 2a. Memory budget on Gaudi2 (v0.4: derived from the HPU allocation code and reconciled with the user's logs)

A card has 96 GB of HBM; the stock run logged `Free device memory: 88.18 GiB, 81.13 GiB usable (gpu_memory_utilization=0.92)`, so about 83.8 GiB are usable at 0.95, of which 10% is reserved for HPU graphs (`VLLM_GRAPH_RESERVED_MEM=0.1`). vLLM replicates KV heads when the tensor-parallel size exceeds the KV head count, so every rank holds one of the two QSA KV heads at TP2, TP4 and TP8: 12 × 1 × 2 × 256 × 2 B = 12.3 KB per token per rank, plus about 0.4 KB of indexer keys. That per-token figure is a lower bound of bytes, not the capacity: the hybrid allocation below decides what fits.

**How the hybrid KV cache is laid out on HPU** (verified 2026-11-17 against the code at the pin and against Run 1 and Run 2; the calculator is spike S4, RUK-2734):

- **One shared block pool.** vLLM at the pin builds one attention group and `n_gdn / n_attn` GDN groups of equal layer count (Flash-Next: 1 + 3 groups of 12 layers; the 27B: 1 + 3 groups of 16), and all groups draw block ids from one pool (`vllm/v1/core/kv_cache_utils.py`, `get_max_concurrency_for_kv_cache_config`).
- **The block size follows the GDN state.** The GDN page per rank is `(48 / TP) × 128 × 128 × 4 B` of FP32 recurrent state plus `(10240 / TP) × 3 × 2 B` of conv state: 391.5 KiB at TP8, 783 KiB at TP4. `vllm_gaudi/platform.py:394–419` pads it to a multiple of the 128-token attention page (128 KiB per layer per rank with BF16 KV), and vLLM's `unify_kv_cache_spec_page_size` raises the attention block size until the pages match: **512 tokens at TP8, 896 at TP4** (1664 at TP4 with FP8 KV). The HPU kernels keep 128-token sub-blocks (`_set_cache_block_capacity`: scheduler blocks versus attention-kernel blocks). A prefix-cache hit needs whole, aligned blocks of this size.
- **Per request under `align`.** With prefix caching on, `mamba_cache_mode` is `align` and a request holds 2 GDN blocks per GDN group (`MambaSpec.max_memory_usage_bytes`), against `cdiv(tokens × 1 KiB, page)` attention blocks: 256 for 131K tokens at TP8.
- **The HPU waste.** The worker cannot share one buffer between BF16 KV and FP32 state, so for each of the `n_attn` layer positions it allocates an attention tensor and a GDN state tensor, both `num_blocks + 1` deep (`vllm_gaudi/v1/worker/hpu_worker.py:1098–1140`, factor `padded_page / (real_attn + real_mamba)`; `hpu_model_runner.py` `_mamba_state_tensors(..., num_blocks + 1)`), and shrinks `num_blocks` to fit. Each attention block therefore carries an unused GDN slot: **43% of the KV budget at TP8, 47% at TP4**. Reconciliation: Run 1 (27B BF16 TP8) logged 72.98 GiB usable, `Usable num_blocks: 5293` and `20.20x`; the model gives 72.98 GiB × 512 / 903.5 ÷ (16 × 512 KiB) = 5293 blocks of 512 tokens and 5293 / (256 + 6) = 20.2×. Run 2 (27B, TP4) logged 19.08×; the model gives 19.2× (block 896, 2941 blocks). Stock vllm-gaudi 0.30.0 has the same worker code, and R3's catalogue shows no upstream change to it.
- **Compact GDN** (`VLLM_COMPACT_GDN=1`, the fork's default) replaces the GDN tensors by a pool of `max_num_seqs × groups × checkpoints + 2` slots and has no waste, but it does not support prefix caching (section 7.1). Today the plugin offers capacity or prefix reuse, not both; the M1 GDN state pool gives both.

- **The PLE short-conv group adds a second shrink factor** (v0.6, 2026-11-17, found while scoping M1). Flash-Next's PLE layer declares a SHORT_CONV `MambaSpec` (180 KiB per slot), which the worker treats as standard Mamba: after the GDN factor it multiplies `available` again by `page / (page + ple_state)` (`hpu_worker.py:1142-1166`), and the runner gives the PLE state a raw buffer of `num_blocks + 1` padded pages. At TP8 BF16 with 40 GiB that is `0.567 x 0.740`: 2,862 blocks, 1.47M KV tokens, about 11 agents at 131K. The Flash-Next "today" cells of the table below carry only the GDN factor and are upper bounds; S4 models both factors from M1-T8 on. The M1 recurrent state pool (plan v0.2) sizes the GDN and PLE tensors to a pool of `max_num_seqs x groups x 3 + 512` slots (896 for Flash-Next at 32 sequences, 4.2 GiB at TP8) and predicts 6,113 attention blocks, 3.13M tokens, 24 agents.

## 7. Workflows this program touches

Line numbers are in `vllm_gaudi/v1/worker/hpu_model_runner.py` unless a file is named; the R2 report on RUK-2719 has the full tables.

1. **Startup.** `HpuPlatform.check_and_update_config` (`vllm_gaudi/platform.py`) forces block size 128 and `mamba_block_size` 128 for Qwen3.5 hybrids (:362–372), realigns `mamba_page_size_padded` (:394–419), turns `mamba_cache_mode` "all" into "align" when prefix caching is on (:454–456), disables prefix caching under `VLLM_CONTIGUOUS_PA` (:447–449) and validates DFlash2 (:136–191: TP1 only, prefix caching off, exactly 7 draft tokens, Qwen3.5/3.8 hybrids only). The runner's GDN group ids are set only for architectures in the allow-list `GraniteMoeHybridForCausalLM`, `Qwen3_5MoeForConditionalGeneration`, `Qwen3_5ForConditionalGeneration`, `Qwen3NextForCausalLM`, `NemotronHForCausalLM` (:927–931): **`Qwen4ExpForConditionalGeneration` must be added** or no GDN state is managed. `VLLM_COMPACT_GDN` defaults to `1` when unset and, with prefix caching on, the runner only warns `Compact GDN mode does not support prefix caching.` (:2172–2181). KV-cache sizing (`hpu_worker.py:1098–1140`, runner `initialize_kv_cache`): with compact GDN off, every layer position gets an attention tensor and a GDN state tensor of `num_blocks + 1` slots and the usable memory is scaled by `padded_page / (real_attn + real_mamba)`; with compact GDN on, GDN state is a pool of `max_num_seqs × groups × checkpoints + 2` slots and the block pool is attention-only (section 2a has the consequences). Then model load with OOT overrides (`vllm_gaudi/models/__init__.py`), KV-cache sizing, warmup over buckets (`vllm_gaudi/extension/bucketing/`, `docs/features/warmup.md`; about 400 s per server in every run so far), graph compilation.
2. **Scheduling and long-prompt prefill.** At the pin the vLLM scheduler gives each step a token budget of `max_num_batched_tokens` (default 2048, `vllm/config/scheduler.py:42`), serves running requests first and admits waiting ones only from what is left (`vllm/v1/core/sched/scheduler.py:509–1189`); `long_prefill_token_threshold` defaults to 0 and there is no `max_num_partial_prefills` at this pin. The HPU runner prefills `max_prefill_batch_size` requests per forward pass, default 1 (`VLLM_PROMPT_BS_BUCKET_MAX`, :2316–2318), and under prefix caching asserts exactly one prefill request per bucket with chunk-aligned context (:4413–4415); merged prefill is forbidden for models with mamba layers (:3633–3634). GDN layers run `hpu_chunk_gated_delta_rule` (`vllm_gaudi/ops/hpu_gdn_pytorch.py`) or the FlashInfer-Gaudi prefill tactic when the shape is TP1 16/48 or TP2 8/24 (`vllm_gaudi/ops/flashinfer_gaudi_adapter.py:58–94`); attention layers run FusedSDPA / paged prefill (`vllm_gaudi/attention/backends/hpu_attn.py`); MoE runs `vllm_gaudi/ops/hpu_fused_moe.py`. Prefix-cache hits reuse attention blocks; GDN state is checkpointed at mamba block boundaries (`compute_prefix_caching_block_indices` :1314, mapping :4417–4460). R7 (RUK-2728) maps the admission path and the knobs.
3. **Decode step.** Decode bucket by batch and blocks; fused GDN decode (`gdn_fused_decode_step`, promoted for TP1 16/48 batches 1–32, TP2 8/24 behind `VLLM_HPU_FLASHINFER_GDN_TP2`); paged attention; MoE; sampler (device sampling since fork PR #58); async scheduling. The fast GDN state paths (`VLLM_HPU_GDN_ASYNC_STATE_DMA`, `VLLM_HPU_GDN_DIRECT_STATE_UPDATE`) require TP2 with no speculation and no prefix caching (:1390–1393), and the direct-state decode path is off whenever prefix caching is on (:2476–2479): at TP4 and TP8 none of them apply.
4. **Speculative decoding.** EAGLE-style proposer (`vllm_gaudi/v1/spec_decode/hpu_eagle.py`, also used for `mtp`), DFlash2 (`hpu_dflash2.py`, `flashinfer_gaudi/dflash2.py`; Qwen3.8-27B draft, TP1 only, greedy only, prefix caching off); Medusa unsupported (:2258); speculation cannot combine with async scheduling (:2307). DeepSeek DSpark is separate. Only EAGLE/MTP drafting is viable for Flash-Next.
5. **Multi-card.** HCCL collectives; TP2 fused AllReduce-norm boundaries (`vllm_gaudi/distributed/tp2_fused_ar_norm.py`); TP4 native replay only for DeepSeek V4.1. `_update_hybrid_attention_mamba_layout` (:8553) is dead code (its only call site, :9060, is commented out).

### Reading

1. **Admission, not memory, sets first-token latency.** Three or four requests ran while four or five waited with 7–8% of the KV cache in use. At the pin the scheduler spends its per-step token budget on running prefills first (section 7.2), so a 128K prompt occupies the budget for about 64 steps at the 2048 default and waiting requests enter only as running ones finish; the stock image's defaults may differ (R7 confirms). The 263 s p99 is queueing.
2. **Decode starves while prefills run.** Aggregate generation of 1.5–2.3 tok/s with 3–4 running requests means decode steps happened only between prefill chunks; the runner prefills one request per forward pass. The "7.1 tok/s per agent" is an average over the whole run, including this phase.
3. **Prefix reuse never paid.** On the stock image the hit rate was 13% falling to 10% on one server and 0% on the other despite a priming pass: the shared prefix is either shorter or less aligned than assumed, or the client's prompts differ early. On the fork, `VLLM_COMPACT_GDN=1` (the default) makes the runner warn and keeps compact state, and the a/a/b check hit 0%; `VLLM_COMPACT_GDN=0` with prefix caching, which upstream vllm-gaudi #1831 qualifies, has not completed a run here.
4. **The fork's FlashInfer-Gaudi GDN tactics may not have engaged** in the TP2 run; the unknown-variable warning is vLLM's and proves nothing either way. R1 names the log line that proves engagement and explains the `Triton/FLA` and `cuda` kernel names.
5. **Warmup costs about 400 s per server at every start**, on both stacks.
6. **Memory**: FP8 27B leaves 2.5M KV tokens per TP4 server on the stock image and 2.15M per TP2 server on the fork; INC FP8 at TP8 leaves 5.19M.

## 14. Program shape and verification model

**Code-complete before rental (since v0.3).** Each milestone ends in a Tech-Lead-reviewed merge into the program branch and a **stage** of the qualification run sheet (`docs/design/flash-next/run-sheets/qualification.md`); no milestone waits for hardware. The CPU gates every change must pass on this Mac:

1. **Import and unit tests**: the plugin and the new model package import on CPU at the pin, and the unit tests S0 records as CPU-runnable stay green.
2. **Eight-rank CPU simulation** (spike S3, RUK-2732): eight `gloo` processes run each sharded layer (linear, embedding, GDN head split, QSA KV and indexer-head replication, MoE sharding, the HyperConnection and PLE paths) at TP1, TP2, TP4 and TP8, compared with the unsharded output, and every rank's collective sequence is recorded and compared. This covers checklist item 5's "per-kernel correctness against unsharded outputs" for every PyTorch path before rental.
3. **Native-code compile check**: the TPC kernels and the C++ bridges (`csrc/`, `tools/build_flashinfer_gaudi.py`, the fused AllReduce bridge) need the Gaudi toolchain (`tpc-clang` from `habanalabs-tools`), which this Mac lacks (no Docker either). They compile on any x86-64 Linux machine with the Gaudi image (`vault.habana.ai/gaudi-docker/1.24.1/...`), no Gaudi card needed. Until the user provides such a machine, native code is written but marked *compile-unchecked* in the run sheet, and stage 1 of the run sheet compiles it first.

What no CPU gate can check, and the run sheet must: HPU graph compilation and recompiles, TPC kernel numerics, HCCL behaviour and latency, memory fit, and every performance number.

**Every new path ships behind a flag, default off**, with the CPU-verified PyTorch path as the default. A failure during the rental session is then answered by turning one flag off, not by debugging on rented time; the logs come back and the fix is made offline.

**The qualification run sheet is ordered fail-fast**, cheapest and most informative first, each stage with a stop rule and the lines to capture: (1) build and native compile; (2) TP8 BF16 startup with the PyTorch paths, memory lines, greedy outputs against the CPU reference on short prompts; (3) flag-by-flag A/B of each native kernel and fusion against its PyTorch path (correctness first, then time); (4) R7's scheduler variants and prefix-cache hit rate; (5) TP1/TP2/TP4/TP8, PP2×TP4 and TP+EP throughput and latency; (6) 128K–262K contexts and the eight-agent stress run with quality checks. Startup costs about 400 s per launch (section 11), so the sheet groups variants by launch and reuses the compile cache (fork PR #62, "reuse completed startup compilation").

Milestones as vertical slices, in the order the reference measurements dictate:

- **M0 Foundations.** Mac CPU environment and test gate (S0); run-sheet template and a replay harness for the agent workload (needs the user's client details); Flash-Next OOT model class on HPU, copied from upstream `nvidia/model.py` + `mtp.py` at the pin with the CUDA seams replaced (torch HyperConnection, torch PLE conv/gate with the table on device, dense paged attention as the first QSA fallback, MoE through the existing HPU path, GDN through `HPUGatedDeltaNetAttention`), the runner's architecture allow-list extended, R4b's carry list applied; first bring-up run sheet at **TP8 BF16 on one server** with correctness checks (greedy outputs against a CPU reference on short prompts) and the memory lines to capture.
- **M1 Admission, prefill and prefix reuse.** Config-only scheduling fixes from R7's run sheet first (per-step budget, long-prefill threshold), then code where the plugin caps it; long-prompt prefill at TP8/TP4 (chunking, GDN prefill for the new head shapes, attention prefill at 128K, bucket shapes, recompiles); prefix caching that hits for the hybrid model (`VLLM_COMPACT_GDN=0` qualification, cherry-picks #1831/#1853/#1828/#1890/#1895, client-side prefix alignment), measured by first-token latency and hit rate on the agent workload. **GDN state pool for prefix caching** (new in v0.4): size the HPU GDN state tensors to the `align` mode's real need instead of `num_blocks + 1` slots, so that prefix caching no longer costs 43–47% of the KV budget (section 2a). Design direction: a reserved block-id range or a second pool for the GDN groups in the scheduler's `BlockPool`, patched in `vllm_gaudi/v1/engine/core_patch.py` (the plugin already patches the scheduler there), so a GDN slot is `block_id − base` and the worker's shrink factor becomes 1; CPU-checked with vLLM's scheduler tests and S3; S4's predicted `num_blocks` and `Maximum concurrency` are compared with the startup log in stage 2 of the run sheet. Fallbacks: compact GDN (no prefix caching) or BF16 GDN state (halves the waste, numerics risk on long contexts).
- **M2 Decode batching.** Fused GDN decode for the TP8 and TP4 shapes, MoE FP8 decode for 512 experts, graph replay and host overhead at batch 16–32, QSA sparse attention proper (indexer + block gather) so long contexts stop paying dense attention.
- **M3 Speculative decoding.** Flash-Next MTP on HPU (upstream `Qwen4ExpMTP` through the fork's EAGLE proposer), IndexShare top-k reuse; DFlash2 only if a Flash-Next draft exists.
- **M4 Two servers and eight cards.** 2 × TP4 with the FP8 checkpoint (block-FP8 MoE on HPU, or INC with the conv1d blocklist) or with PLE host offload (backport #54371 or the fork's Engram host gather); TP8 versus 2 × TP4 versus TP + EP; HCCL topology on the HLS-2.
- **M5 Gaudi2 extras.** Whatever the profiles show (FP8 KV, native fusions already in FlashInfer-Gaudi, warmup time, sampler).
